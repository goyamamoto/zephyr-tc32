# Zephyr for the Telink TC32: the TLSR8278

This tree is Zephyr v4.5.0-rc1 with support for Telink's TC32 CPU and the TLSR8278 SoC. Apart from the files listed under [Upstream files changed](#upstream-files-changed), upstream is unchanged.

- **Architecture layer:** `arch/tc32`, the `tlsr827x` SoC series, and the GPIO and system timer drivers. They come from devbis's [zephyr-tlsr8258](https://github.com/devbis/zephyr-tlsr8258), as the first commit after v4.5.0-rc1, which has that tree's names (`tlsr825x`, `tlsr8258`).
- **TLSR8278 support:** the SoC, the drivers, the random number generator and the build, on top of it.
- **Licence:** Apache-2.0, as upstream's. `NOTICE` names the authors and the third-party code.

The code runs in [TC32-devtools](https://github.com/goyamamoto/TC32-devtools)' emulator and, on TLSR8278 hardware, in keyboard firmware built on it ([zmk-tc32](https://github.com/goyamamoto/zmk-tc32), [tc32-keyboards](https://github.com/goyamamoto/tc32-keyboards)).

## What is supported

Names follow upstream's Telink B91 support. The TLSR8278 belongs to Telink's B87 family: the series is `tlsr827x`, the compatibles are `telink,b87-*`, the drivers `<class>_b87.c` and their options `<CLASS>_TELINK_B87`. The SoC keeps `tlsr8278` (`SOC_TLSR8278*`, the `tlsr8278_*.h` headers).

| Area | What | Option |
|---|---|---|
| CPU | TC32 (ARMv4T Thumb, re-encoded), interrupts through the port's dispatcher, the hardware divider for 32-bit division, fast 64-bit division, soft float (compiler-rt) | `TC32` |
| SoC | Power-on setup (supplies, 48 MHz from the 24 MHz crystal, RC calibration), startup from reset, an early watchdog, suspend with wake by pad, USB or timer, deep sleep, suspend from the idle thread | `SOC_TLSR8278*` |
| System timer, GPIO | The architecture layer's drivers, with the TLSR8278's registers | `TELINK_B87_TIMER`, `GPIO_TELINK_B87` |
| USB | Device controller for the USB device stack (`device_next`): full speed, 8-byte EP0, bulk and interrupt up to 64 bytes, remote wakeup | `UDC_TELINK_B87` |
| Flash | The internal flash: read, page program, sector erase, page layout | `SOC_FLASH_TELINK_B87` |
| hwinfo | Device ID (the flash's 128-bit unique ID), reset cause | `HWINFO_TELINK_B87` |
| Watchdog | Timer2 | `WDT_TELINK_B87` |
| Pin control | Pin functions, pull resistors, input enable | `PINCTRL_TELINK_B87` |
| Clock control | Module clocks | `CLOCK_CONTROL_TELINK_B87` |
| ADC | SAR ADC, misc channel, PB0-PB7, PC4, PC5, gain 1, 13 or 14 bits | `ADC_TELINK_B87` |
| SPI | Master, modes 0-3, 8-bit frames, half duplex | `SPI_TELINK_B87` |
| Radio | The radio's registers for BLE 1M and a private 2M mode; the link layer is the application's | `SOC_TLSR8278_RADIO` |
| Random numbers | `tc32_rng`, a generator with several sources (below) | `TC32_RNG` |
| AES-128 | On the AES block or in software | `TC32_AES128` |
| P-256 | Point multiplication and point checks for LE Secure Connections, in software or on the public key engine | `TC32_P256` |
| Emulator console | printk, stdout and log output for images run in the emulator | `TC32EMU_CONSOLE`, `LOG_BACKEND_TC32EMU` |

The drivers' nodes in `dts/tc32/telink/tlsr8278.dtsi` are disabled by default.

**The public key engine.** DS-TLSR8278 chapter 16 gives the engine's registers and operand RAM, but not which operand slot each of its routines reads. `soc/telink/tlsr/tlsr827x/tlsr_pke.c` uses the slots and the register sequence of Telink's driver for the same engine on the B91 (`tlsr9/drivers/B91/pke.c` in Zephyr's [hal_telink](https://github.com/zephyrproject-rtos/hal_telink), Apache-2.0) and the routine numbers of Telink's B87 `pke.h` (Apache-2.0). On the TLSR8278 they were confirmed with known answers: the Bluetooth Core specification's debug key pair, a pairing recorded in Apache NimBLE's host tests and its shared secret, and a point off the curve.

`boards/telink/tlsr8278_generic` is a board for the emulator: 64 KB SRAM, 1 MB flash, no flash runner ([doc](boards/telink/tlsr8278_generic/doc/index.rst)).

## Not provided

- **The legacy USB device stack** (`USB_DEVICE_STACK`). Its samples and tests do not build for this SoC. The keyboard firmware built on this port (zmk-tc32) keeps the legacy stack for its smaller size and carries its own driver for it.
- **An entropy driver.** The chip's random bit generator is read only by `tc32_rng`, so Zephyr's random options have no entropy device on this SoC.
- **CPU fault exceptions.** What the TC32 does on an invalid instruction or fetch is not documented. The kernel tests that trigger one skip on TC32 (`CONFIG_TEST_NO_CPU_EXCEPTION`).
- **Interrupts:** no direct interrupts (`IRQ_DIRECT_CONNECT()`), and no interrupt priorities or nesting yet. The hardware's two priority levels are not used.
- **Power management:** not through Zephyr's PM subsystem. Suspend is the SoC's own idle hook (`SOC_TLSR8278_IDLE_SUSPEND`).
- **Peripherals:** UART, I2C, PWM, counter, QDEC, the audio path, the AES-CCM hardware, a BT controller, IEEE 802.15.4.
- **Hardware coverage:** the drivers above have run on hardware only as far as that keyboard firmware uses them.

What can misbehave, what is assumed and what each such gap's test is: `TC32-gaps.md`.

## Random numbers

Applications get random numbers from three functions of `tc32_rng`:
- `tc32_rng_get()` and `tc32_rng_get_key_material()`, for cryptographic use;
- `tc32_rng_fill()`, for values that need no secrecy.

Zephyr's random subsystem is left unchanged; `tc32_rng` does not provide `sys_rand_get()` or `sys_csrand_get()`.

**Sources.** None of them is trusted alone.
- The random bit generator's raw output: no credit by default.
- The jitter of the 32 kHz RC oscillator against the system timer.
- The ADC's noise on VBAT, health-tested (SP 800-90B RCT and APT) and range-checked.
- Events the application feeds in.
- A seed record the application stores.
- The device ID.

**Construction.**
- A 16-byte CBC-MAC pool under a secret key that changes at every reseed.
- An AES-128-CTR generator with fast key erasure.
- A Davies-Meyer reseed.

**Readiness.** Nothing is output for cryptographic use until 128 bits have been credited since boot, either from a valid seed record or, on a first boot, from the jitter and the ADC (about 55 ms). `tc32_rng_collect()` gives up with `-ETIMEDOUT` (`TC32_RNG_COLLECT_TIMEOUT_MS`).

**Size.** About 2.1 KB of flash and 88 bytes of RAM, plus 144 bytes for the AES block.

`subsys/tc32_rng/tc32_rng.c` explains each step.

## Building

**Requirements:**
- clang and ld.lld, LLVM 16 or later. Use Zephyr's `host/llvm` toolchain variant, with `LLVM_TOOLCHAIN_PATH` set to the directory whose `bin/` holds them.
  - `TC32_POP_PC_RETURNS` needs [llvm-tc32](https://github.com/goyamamoto/llvm-tc32). With that option, functions return with `pop {..., pc}`. The configuration checks the compiler.
- [TC32-devtools](https://github.com/goyamamoto/TC32-devtools):
  - `tc32asm2thumb.py` translates the port's assembly.
  - `thumb2tc32.py` writes the TC32 image (`elf2bin.py` on the direct path).
  - `image_check.py` and `forms_check.py` check it; `asm_twin_check.py` compares each assembly source with its twin.
  - `run-boot` (Go) or `run_boot.py` runs it in the emulator.

  The build finds it through `TC32_DEVTOOLS`, and the emulator through `TC32EMU`.
- Zephyr's own requirements.

```sh
export ZEPHYR_BASE=$PWD TC32_DEVTOOLS=/path/to/TC32-devtools TC32EMU=$TC32_DEVTOOLS/go/bin/run-boot
cmake -S tests/arch/tc32/softfloat -B build -GNinja -DBOARD=tlsr8278_generic \
  -DZEPHYR_TOOLCHAIN_VARIANT=host/llvm -DLLVM_TOOLCHAIN_PATH=/path/to/llvm -DTC32_THUMB=ON
cmake --build build
cmake --build build -t run
```

- `zephyr.elf` is the ARMv4T Thumb link.
- The build also writes the TC32 image `zephyr.tc32.bin`, which starts with the boot header the ROM reads, and checks it against the ELF.
- `run` boots the image in the emulator and prints the console.

### Two paths to the image

| | Thumb path (default) | Direct path, `-DTC32_DIRECT=ON` |
|---|---|---|
| Compiler | any clang, `-mcpu=arm7tdmi -mthumb` | llvm-tc32, `-mcpu=tc32 -mthumb` |
| Assembly | `<name>.S` (Telink's mnemonics) through `tc32asm2thumb.py` | its twin `<name>.ual.S` (standard syntax), as it is |
| `zephyr.elf` | ARMv4T Thumb | TC32 code (Tag_CPU_name `tc32`) |
| Image | `thumb2tc32.py` re-encodes the link | `elf2bin.py` lays out the link |

- Both paths generate the same code, so the same sources give byte-identical images. The two encoders check each other: TC32-devtools' `path_diff.py` compares the two images and names the symbol at any difference.
- The direct path needs `-DTC32_THUMB=ON` as well; the configuration stops when the compiler does not take `-mcpu=tc32`.
- The core `tc32` has the `noarm` feature. Without `TC32_POP_PC_RETURNS`, the direct path compiles C with `-noarm`, so returns are the same as on the Thumb path. The units named by `tc32_classic_returns()` keep the classic return on both paths.
- Every Telink-mnemonic source has a twin: `arch/tc32/core/{reset,switch}.ual.S` and `soc/telink/tlsr/tlsr827x/setup/{tlsr8278_startup,tlsr8278_setup}.ual.S`. On both paths each build assembles the translation and the twin with the same flags, and `asm_twin_check.py` compares the two objects: sections, relocations, symbols and build attributes. A change to one file without the other fails the build. `tlsr8278_setup.h` is a C header and serves both.

## Testing

`tlsr8278_generic` runs its images through the `run` target (`cmake/emu/tc32emu.cmake`), so twister builds and runs tests for it:

```sh
export ZEPHYR_TOOLCHAIN_VARIANT=host/llvm LLVM_TOOLCHAIN_PATH=/path/to/llvm
scripts/twister -p tlsr8278_generic -j 2 -T tests/kernel -T tests/arch/common -x TC32_THUMB=ON
```

Add `-x TC32_DIRECT=ON` for the direct path, with `LLVM_TOOLCHAIN_PATH` at llvm-tc32.

The test suites:
- **Kernel and architecture:** `tests/kernel` and `tests/arch/common` pass 95 of 107 configurations, with no failures. The other 12 are 11 that do not fit the RAM and one long soak test that twister does not run.
- **The port's own:**
  - `tests/arch/tc32/softfloat` and `tests/arch/tc32/udiv64_const`;
  - `tests/subsys/tc32_rng`, which uses the emulator's fault injection for the TRNG, the 32 kHz timer and the ADC;
  - `tests/crypto/tc32_p256`, one scenario per P-256 implementation, with the Core specification's debug key pair and a pairing recorded in Apache NimBLE's host tests;
  - `tests/drivers/{hwinfo,watchdog,pinctrl,clock_control,adc,spi,flash}/tlsr8278`.
- **Upstream driver tests:** `tests/drivers/{hwinfo/api,watchdog/wdt_basic_api,adc/adc_api,flash/common,udc}`.
